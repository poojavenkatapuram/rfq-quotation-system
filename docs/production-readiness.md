# Production readiness runbook

This document describes operating guidance; it does not deploy the application or run migrations.

## Configuration

Set server variables through the deployment secret manager. Never commit real values:

- `DATABASE_URL`: PostgreSQL connection string for the intended environment.
- `JWT_SECRET`: at least 32 random characters.
- `CLIENT_URL`: HTTPS browser origin.
- `TRUST_PROXY_HOPS`: integer from 1 to 5 matching trusted reverse proxies.
- `RFQ_DOCUMENT_STORAGE_DIR`: absolute path on a persistent private volume owned by the service account.
- `LOCAL_AI_ENABLED=false`: keep local model suggestions disabled unless their deployment is separately reviewed.
- `OLLAMA_RFQ_MODEL=qwen2.5:1.5b`: choose a locally installed and evaluated model; model-name overrides are validated.
- `OLLAMA_RFQ_NUM_GPU=0` and `OLLAMA_RFQ_NUM_THREAD=4`: use bounded CPU-only inference settings on small hosts; validate the thread limit against the deployed CPU allocation.

The server validates production configuration when `NODE_ENV=production`. New document directories and files receive owner-only permissions. Do not serve the document directory through the web server. Set frontend `VITE_API_BASE_URL` at build time to the API URL ending in `/api`. Keep the API on a private interface behind the trusted TLS reverse proxy.

## Local AI status and data handling

The supported endpoint is local Ollama at `http://127.0.0.1:11434/api/generate`; the model is configured locally. One bounded synthetic service-level test using `qwen2.5:1.5b`, `num_gpu=0`, and `num_thread=4` returned one validated cycle-time suggestion in 137.8 seconds (model load 76.9s, prompt evaluation 30.8s, generation 28.3s). A prior request with the default thread count timed out at the configured 180-second limit; browser/database completion after adding the thread limit has not been verified. Local inference works in a tested request but is not yet reliable enough to promise an operational response time. Deterministic extraction remains available. Do not send customer RFQ documents to external AI services. When inference is enabled, AI suggestions remain supplementary, require literal evidence and human acceptance, and do not calculate price, tax, or quotation totals.

Routing recommendations come from historical similarity matching and are traceable to matching historical data; they are not generated by Ollama.

## Database migrations

The Phase 6D isolated test applied the repository's 11 migrations to the empty `forgeflow_synthetic_demo_test` database on localhost. That was a test-only database, not a production deployment. Never point production or a business database at a test command.

For a future approved deployment:

1. Confirm the exact database target and owner, and verify it is the intended environment.
2. Create and verify a backup using the procedure below.
3. Run `npx prisma migrate status` against the intended target.
4. Review the already checked-in migration SQL and obtain the required approval.
5. Run `npx prisma migrate deploy` once in an approved maintenance window.
6. Check `/api/health/database`, sanitized application logs, and a read-only smoke workflow.

Do not use `prisma db push` or `prisma migrate reset` against a database containing application records. Migration rollback is a specifically approved database restore operation, not an automatic application command.

## Backup and recovery rehearsal

`server/scripts/backup-postgres.sh` creates a timestamped custom-format dump with mode `0600`, refuses to overwrite an existing backup, and writes a SHA-256 sidecar. It requires PostgreSQL client tools and these privately supplied variables:

```bash
export DATABASE_URL='postgresql://...'
export BACKUP_DIRECTORY='/secure/backup/rfq-quotation'
./server/scripts/backup-postgres.sh
./server/scripts/verify-postgres-backup.sh /secure/backup/rfq-quotation/rfq-quotation-YYYYMMDDTHHMMSSZ.dump
```

For a recovery rehearsal, restore only into a newly created, isolated staging database. Verify `pg_restore --list`, restore with a database administrator present, run the server's read-only health check, and compare record counts. Do not run destructive restore flags against a live database without an approved recovery plan.

## Operational controls

- Use an edge-level shared login rate limit for multi-instance deployments; the application limiter is process-local.
- Restrict database network access to the application service identity and use encrypted connections where supported.
- Rotate JWT, database, and bootstrap credentials through the secret manager.
- Centralize sanitized logs and alert on repeated 401/429 responses, extraction failures, database health failures, and storage write failures.
- Retain audit logs/backups according to the organization's NDA and retention policy. Do not copy drawings into logs, external AI services, or public object storage.
